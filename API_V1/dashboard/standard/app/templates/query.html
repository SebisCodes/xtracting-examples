Query

About this page

Search the archive's sources and their attributes within a place on the world, with a radius, in a date range.

What to find decides which kind of object comes back. The search itself is always the same walk: the locations that answer the place, the entities standing at them, and the objects hanging off those entities. One kind at a time, because each one is a pass over every location of the place and two of them is twice the wait.

Say where either by naming a place or by giving a point and a distance - never both; the line under the field says which is in force.

With no words at all, everything written about the place is listed. A date preset sets the start and leaves the end open.

Where {#- A REAL EITHER/OR, and only one of the two on the page. Not an address field with a disclosure under it - "Use coordinates and a distance instead" - which puts both ways of naming a place on screen at once, while the server refuses a request that carries both (400: "a place or a point, not both"). A form that offers two things and accepts one is a form that can only be learned by getting it wrong. The switch is the one every other view has, in the same markup and with the same label, so a reader who has seen it on Diagrams or on the Map already knows what it does. The half that is not chosen is `hidden` - out of the page and out of the tab order, not merely folded away. Eight suggestions, not the macro's twelve: the same ten-row ceiling the Events fields keep to, and an address is a long row. The hint keeps the half that stops a mistake - only the archive's own addresses are found here - and drops the half that describes their shape; that is in the About disclosure. A TOOLBAR, so the label row is a fixed 24 px and the control lands on the same baseline as the chips box beside it and the two date fields beside that (tests/ui/test_query_layout.py measures it). -#}

{#- ── WHAT THE ANSWER IS ABOUT, BEFORE THE ANSWER ────────────────────── THE CASE THIS IS FOR: a search of Houston for oil and gas comes back with hundreds of documents about one politician. Nothing is wrong with the search - he really is in all of them - and there is no search term that means "not him". Narrowing by hand would mean guessing a word. So the answer names its own subjects first. Every entity the place holds, with how many rows of the chosen kind it accounts for, and a tick each: untick the ones the question is not about and ask again. The exclusion goes into the scope the search runs through (routers/api_query.py), so it holds for every kind of object and not only for the one on screen. ORDERED BY HOW MUCH OF THE ANSWER EACH ONE IS, so the ones worth excluding are at the top and nobody scrolls to find them. The two boxes narrow the list itself - a name and a type, the two columns - and they narrow what is SHOWN, never what is ticked: a filter that silently unticked what it hid would throw away a decision. IT IS NOT A SECOND SEARCH BUTTON. The list arrives with the results, in its own request, so a reader who wanted the answer has the answer; the ticks only matter to the NEXT press. -#}
